# DOW — src/gnostr/

## Purpose
Core application layer — GTK4 window, app lifecycle, Nostr client wiring, and signal handling. This is the backbone that connects UI widgets to the Nostr protocol layer.

## Ownership
- `main.py` — MainWindow class (window init, UI layout, signal handlers, login flow; `sync_follows()` shared follow-sync push + `show_follows(owner_pubkey)` opens the Follows list) and GnostrApp class (app activation)
- `window.py` — window.ui builder integration
- `client.py` — NostrClient: relay connections, subscriptions, event publishing. **DM self-copy contract:** `publish_dm` stores the local self-copy with PLAINTEXT content (threads/inbox read `dm_messages` directly and nothing re-decrypts our own rows); the published event keeps the NIP-44 ciphertext. The relay echo of our own kind-4 is a harmless PK-collision no-op and must never be routed to `dm_service.schedule_decrypt`. **DM freshness poll:** `ensure_dm` arms `start_dm_poll()` — a `GLib.timeout_add` every `DM_POLL_INTERVAL` (60 s) that fires `_dm_poll_tick`: one snapshot REQ (`dm_poll_<seq>`, kind-4 `#p`=us, `since=now-interval-slack`) per relay via `request_once`. This exists because `subscribe()` CLOSEs the previous sub_id when a different one opens — visiting the feed closes `dm_sub` and new DMs would otherwise surface only on manual refresh. Unique sub_id per tick (REQ dedup keys on sub_id); snapshot = auto-close on EOSE, never replayed, never disturbs a live `dm_sub`. `set_keys(None, None)` (logout) and a no-pubkey tick both stop it. `main.py` connects `dm-conversations-updated` → `update_dm_badge` so poll-delivered DMs move the sidebar badge while the user is on the feed. Tests: `tests/test_dm_poll.py`.
- `database.py` — Database: SQLite storage for events and profiles
- `dialogs.py` — LoginDialog, RelayPreferencesWindow, ComposeWindow, resolve_login_input (single login-secret decision point), ExportKeyDialog
- `key_manager.py` — KeyManager: nsec storage/retrieval via libsecret
- `nip49.py` — NIP-49 `ncryptsec` portable backup crypto (pure Python, stdlib-only; sole home of the vendored XChaCha20-Poly1305 — verified byte-identical to libsodium + official NIP-49 vector; do NOT replace with nacl/cryptography, the Flatpak runtime lacks both)
- `nip06.py` — NIP-06 seed-phrase key derivation: BIP-39 (validate + PBKDF2 seed, vendored `bip39_wordlist_english.txt`) + BIP-32 CKDpriv + `derive_keypair()` at m/44'/1237'/<account>'/0/0 (SLIP-0044 Nostr entry). Pure functions, stdlib + ecdsa only, no GTK — same testability contract as nip49.py/nip44.py. NIP-06 is `unrecommended` by its own NIP: expose it ONLY as an explicit power-user option with the warning visible
- `key_health.py` — last-backup-verified timestamp store (`key_health.json` beside gnostr.db). Stores NO key material — only a unix ts written by ExportKeyDialog when a backup artifact is produced; Settings/sidebar renders it via `format_last_backup`
- `nostr_utils.py` — bech32 encode/decode, key derivation, event signing
- `profile_nips.py` — profile NIP helpers (NIP-05 verify, NIP-39 identities, NIP-58 badges, LUD-16)
- `connection_status.py` — relay status enum
- `renderer.py` — ContentRenderer, ImageLoader, VideoPlayer, VideoLoader

## Local Contracts
- `main.py` owns app startup and window construction. All widget instantiation happens here
- **FAB compose icon:** `main.py` `_resolve_fab_icon()` picks the new-post FAB glyph against the active icon theme (document-edit-symbolic -> document-new-symbolic -> list-add-symbolic, first `has_icon()` hit wins). Do NOT hard-code `edit-create-symbolic` — it does not exist in Adwaita/Phosh and rendered the FAB blank/wrong (same class of bug as the footer `chat-bubble-symbolic` fix in PostWidget; same resolution pattern as `PostWidget._resolve_icon_name`)
- Window layout: Adw.ToastOverlay → Adw.ViewStack → split_view. FAB floats on content-area Gtk.Overlay, not a global overlay — toast overlay stays constrained to window size
- **Toast width vs narrow screens**: libadwaita's `.toast` node has a fixed 368 px width (+margins ≈ 384 px min). A 360 logical px window (Librem 5: 720 px panel at scale-factor 2) cannot fit it — AdwToastOverlay warns `exceeds MainWindow width` and clips. Fix lives in the GnostrApp CSS provider (`.toast { min-width: 0; }` + `@media (max-width: 400px)` cap to 320 px); keep toasts window-constrained, do NOT restructure the overlay tree to work around it
- `client.py` is the sole relay communication layer — UI code never opens WebSockets directly
- Subscription management: `subscribe()` CLOSEs the previous subscription before sending a new REQ to prevent relay REQ floods. Each relay tracks `active_sub_ids` (sub_ids actually opened on THAT relay) and only CLOSEs IDs it opened — the old single shared `self.sub_id` sent CLOSE for unrecognized IDs, producing "bad close: invalid subscription id length" + "too many concurrent REQs" NOTICEs that degraded relay communication
- **Relay usage economy (issue #26):** `client.py` owns the REQ economy — a token-bucket REQ rate limiter (`REQ_RATE_LIMIT` 18/s per relay, `REQ_BURST` 5; nos.lol bans at 200 REQ/10 s per IP), queue dedup (`REQ_DEDUP_WINDOW` 2 s: the same sub_id queued twice is one REQ), `live_subs` (persistent sub_id -> filters; reconnect replays ONLY these through the rate-limited queue — snapshot subs never replay, they auto-close at their EOSE), the NIP-01 `CLOSED` handler (a refused sub is dropped from active/queued/snapshot/live sets so it is never re-REQ'd — the ban spiral; a rate-limit reason prints once per connection), `restart()` randomized exponential backoff (`RECONNECT_BACKOFF_START` 2 s -> `RECONNECT_BACKOFF_MAX` 60 s, reset on CONNECTED), and idle parking (`check_connections` parks a relay with no inbound traffic for `IDLE_RELAY_TIMEOUT` 300 s and no live sub; a deliberate park never emits DISCONNECTED status; `subscribe`/`request_once` wake a parked relay and drain the queue). Tests: `tests/test_relay_usage_economy.py`.
- **Publish observability:** `relay.publish()` returns True/False and logs when a relay is not connected or the send fails (was silently swallowed). `NostrClient.publish()` logs `EVENT <id> sent to N/M relay(s)` so the like/follow flow shows exactly how many relays received it — relay communication is never silently dropped
- `renderer.py` handles ALL content display rendering (text, images, video, nostr cards). UI widgets call `ContentRenderer.render()` and insert the returned box
- `database.py` is the single persistence layer — no other module writes to SQLite
- `database.get_replies(parent_id)` filters by the parent's e-tag BEFORE applying LIMIT (tags stored as JSON text; a LIKE match narrows candidates, then precise Python filter) so old replies aren't silently dropped by the global newest-50 cut
- **Social actions (NIPs):** the protocol event-builders live in `nostr_utils.py` (GTK-free, unit-testable, one place to refactor) — `build_reaction_event` (NIP-25 kind 7, tags `[["e",id],["p",pk]]`, content `+`/`-` for like/undo), `build_repost_event` (NIP-18 kind 6, content = original event JSON, tags `[["k",kind],["e",id],["p",pk]]`), `build_reply_event` (NIP-01 kind 1, root `e`-tag first + direct-parent last + `p`-tags for both authors). `client.publish_post(content, reply_to=...)`, `client.publish_reaction(eid, pk, content)`, `client.publish_repost(eid, pk, kind, original_event)` all route through `_build_and_publish` (build→sign→publish, DRY); replies thread root-first/parent-last so both metrics (`get_ref_id` first e-tag) and the reply tree (last e-tag) stay correct. `database.user_reaction(eid, pk)` returns the user's most recent kind-7 content (like-toggle state)
- **NIP-19/NIP-21 nostr types:** the bech32 decode layer lives in `nostr_utils.py` (GTK-free) — `decode_naddr` (kind:pubkey:d-tag coordinate + relays), `decode_nevent_full` (event id + relay/author/kind hints), `decode_nprofile` (pubkey + relays), all via the shared `_decode_tlv` parser (unknown TLVs ignored per NIP-19). `is_nostr_reference` covers nevent/nprofile/naddr/nrelay/note/npub. `renderer.py` routes `nostr:naddr` to `_add_naddr_card` (quote card resolved by coordinate via `database.get_event_by_a`), `nostr:nrelay` to a plain link, and `nostr:note`/`nevent` to `_add_nostr_card` (honors the nevent relay hint). Both share `_build_quote_card` (DB check → fetch if missing → register pending card on the PostWidget's `quote_widgets` list → wire click). `client.py` emits `quote-event-received` (full event JSON) for EVERY kind after `save_event` — addressable events (kind 30000-39999) never hit the kind-1 event-received path, so this is their only route. `main.py` w: `on_quote_event_received` matches pending cards by event id (` ("id", hex)`) or coordinate (`("a", kind:pubkey:d-tag)`) and populates them via `_build_quote_content`. `database.get_event_by_a(kind, pubkey, d_tag)` returns the newest addressable event for
- **Profile NIPs (NIP-05/24/39/57/58):** the GTK-free protocol helpers live in `profile_nips.py` — `verify_nip05` (DNS identity check via `https://<domain>/.well-known/nostr.json?name=<local-part>`, returns False on any failure), `parse_external_identities` (NIP-39 kind-10011 `i`-tags → platform/identity/proof/url), `parse_profile_badges` (NIP-58 kind-10008 ordered a/e pairs), `resolve_lnurl_endpoint` (LUD-16 lightning address → lnurlp URL). `database.py` persists all NIP-01/NIP-24 metadata fields (name, display_name, about, picture, website, banner, nip05, lud16, bot, birthday, raw_json) plus `external_identities`/ JSON columns and a `badge_definitions` table (kind-30009, keyed by coordinate). `client.py` handles kind 10011 (→ `save_external_identities` + `external-identities-updated`), kind 10008 (→ `save_profile_badges` + `badges-updated`), kind 30009 (→ `save_badge_definition`); `publish_profile(metadata)` builds + signs + publishes a kind-0 event (tracked as `Profile` in pending_publishes) and persists locally; `fetch_external_identities`/`fetch_badges` are TTL-cached kind-10011/10008 requests. `profile_view.py` renders banner, bio, website, verified nip05 (async), lightning address, external identities, badges, and following count; `dialogs.EditProfileDialog` edits + publishes the user's own kind-0 metadata.
- **Publish OK acks (NIP-01):** relays ack EVENT publishes with `["OK", <event_id>, <true|false>, <message>]`. `nostr_utils.parse_ok_message()` is the pure GTK-free parser; `NostrRelay.on_msg` routes OK → `on_ok`; `NostrClient` tracks just-published events in `pending_publishes` (event_id → label + 30s expiry), resolves them in `_handle_ok`, and emits `publish-result` (event_id, accepted, message, relay_url, label). `sweep_pending_publishes()` retries untried candidates then settles expired entries (dead relays). **DM-3 resilient publish:** the pending entry also carries the signed event + `tried`/`answered`/`rejections`/`candidates`; the first OK accepted=true settles the publish (dedupe — later relay acks are ignored, no duplicate delivery). An OK accepted=false logs the rejecting relay and `_retry_publish()` re-sends the event on every candidate relay not yet tried — `_send_to_relay` connects a fallback relay on demand and queues the EVENT on it until its socket opens (`NostrRelay.publish_queue` flushed in `on_open`); `publish-result` fires only after all candidates answered (aggregated failure message names the last rejecting relay) or the sweep expires the entry. DM publishes pass `candidates=` = the peer's 10050 relays (`_publish_dm_targeted`); general publishes retry across the configured `relay_urls` (`publish()` returns the sent-relay URL set). `main.py` surfaces these as `Adw.Toast` ("Liked ✓" / "Follow failed: <msg>") and runs a 15s sweep timer. Kind-3 follow publishes register with a Follow/Unfollow label through `_publish_contact_list`. Tests: `tests/test_relay_retry_publish.py`
- **Relay activity log:** `NostrClient.relay_log` is a bounded deque (200) of `[HH:MM:SS]` activity lines; `_log_relay()` appends + emits `relay-log-updated` (line). Wired into `_track_publish` (sent + relay count), `_handle_ok` (OK/REJECTED + relay), `sweep_pending_publishes` (NOT CONFIRMED), and `_handle_status` (connect/disconnect). `main.py` routes the signal to the sidebar's Relay Activity pane — so follows/likes/reposts are verifiable against relays, not just the DB
- `key_manager.py` is the single key storage layer — no plaintext key files anywhere
- **Onboarding and secure login (spec: `docs/onboarding-key-management.md`; P1 IMPLEMENTED, P2/P3 pending)**: P1 adds create-account plus un-skippable backup gate plus NIP-49 `ncryptsec` import and export (NIP-49 is a portable backup format only; libsecret remains the at-rest store). P2 adds a `signer/` module: `SignerBackend` interface (LocalKeyBackend = today's priv_key signing, BunkerBackend = NIP-46 remote signing); client.py and main.py must go through the backend, never hold raw priv_key directly. Until implemented, current contracts stand
- `dialogs.py` owns all modal dialogs. Call `.present()` on the dialog, never construct GTK windows inline
- **Signing funnel pubkey fill:** `NostrClient._sign` fills a missing `event["pubkey"]` from `my_pubkey` (on a copy — never mutates the caller's dict) before delegating. `compute_event_id` indexes `event["pubkey"]` directly and `sign_event` swallows the KeyError into None, so any builder that omits pubkey (blossom BUD-01 auth events) silently kills uploads. Tests: `tests/test_sign_funnel_pubkey.py`
- **Clipboard (GTK4):** `Gdk.Clipboard` has NO `set_text()` — that was GTK3's `Gtk.Clipboard`. The GTK4 write API is `clipboard.set_content(Gdk.ContentProvider.new_for_value(text))`. A `set_text` call raises AttributeError inside the signal handler, PyGObject swallows it to stderr, and the Copy button silently does nothing (issue #33; guarded by `tests/test_clipboard_api.py` source scan + `tests/test_clipboard_gtk_real.py` real read-back). Always obtain the clipboard via `Gdk.Display.get_default().get_clipboard()`, never construct `Gdk.Clipboard(display)`

- **Package init import order:** `gnostr/__init__.py` imports `profile_nips` FIRST (before `client`). `client.py` does a module-level `import gnostr`, so importing `profile_nips` after `client` left the partially-initialized `gnostr` package without `profile_nips` as an attribute — Flatpak startup failed with `cannot import name 'profile_nips' from partially initialized module 'gnostr'`. `profile_nips` is stdlib-only (no package deps), so it must stay first in the init chain. Regression test: `tests/test_package_import.py`.

- **Flatpak install list:** every new core module in `src/gnostr/` MUST be added to the `install_data` list in `src/gnostr/meson.build` — otherwise the Flatpak build does not ship it to `/app/share/gnostr/`, and `__init__.py`'s `from . import <mod>` fails at startup with `cannot import name '<mod>' from partially initialized module 'gnostr'` (the file simply isn't installed). `profile_nips.py` was missed this way. Check `ls src/gnostr/*.py` against the install list when adding a module.

- **Follower sync (DB ↔ relays):** PULL — on first relay CONNECTED, `main.on_status_changed` calls `client.fetch_contacts` (kind-3 sub for own pubkey, limit 1); `client.fetch_contacts_for(pubkey)` fetches ANY user's kind-3 (used by FollowersListView refresh). Arriving kind-3 from ANY author → `_handle_event` reconciles THAT author's `following` rows wholesale via `save_contacts(pubkey, …)` (the table is owner-keyed, so foreign lists populate their own rows — this is how the Follows list gets data for other profiles); the `kind-3 received: N follows reconciled` log line and relay-hint merge (kind-3 content JSON) stay own-pubkey-only. `contacts-updated` carries the pubkey; an open FollowersListView reloads when it matches. PUSH — the old sidebar `Follow Sync` row is now a `Follows` row opening the own list; the sync behavior lives in `main.sync_follows()` (`client.sync_followers()` re-publishes the CURRENT DB following list as kind-3 via `_publish_contact_list(label="Follow Sync")` — kind-3 is replaceable; relays swap the list), shared by the own-profile `Sync Follows` button and the own-list sync button, tracked for OK acks so the pane/toast confirms landing. `publish_contacts()` now delegates to `_publish_contact_list` (was a duplicate untracked builder). Tests: `tests/test_follow_sync.py` — NostrClient subclasses mocked GObject so its methods aren't importable; tests extract the real functions from client.py source via ast and bind them to a FakeClient.
- **Search (identifier → profile):** `nostr_utils.resolve_profile_identifier(text)` maps a pasted Nostr identifier to a 64-char hex pubkey (or None): npub (via new `npub_to_hex`), nprofile, nsec (own key via `nsec_to_hex` + `get_public_key`), raw 64-char hex, and a `nostr:` URI prefix; nevent/naddr resolve to their author pubkey only when the NIP-19 TLV carries the hint. `dialogs.SearchDialog` (Adw.Window) collects the identifier, resolves it, and on success calls `main_window.show_profile` then closes; on failure shows a `Not a valid Nostr identifier` toast. `main.show_search_dialog()` launches `SearchDialog`. No relay-side text search (NIP-50) — identifier resolution only.

## Work Guidance
- MainWindow connects client signals in `__init__`: event-received, status-changed, contacts-updated (carries the reconciled pubkey — own or foreign), profile-updated, metrics-updated
- Login flow: KeyManager.load_key() → perform_login() → switch stack to "app" view. **perform_login MUST call `client.set_keys(pub, priv)`** — the fresh-login dialog path sets keys, so the saved-key startup path must too, or `publish_*` (like/repost/reply/follow) silently no-ops with "No private key loaded"
- Feed switching (model-driven): `switch_feed(feed_type)` clears `event_widgets` + `posts_box`, builds a `service.feed_model.FeedModel(db, page_size=20, max_window=30)`, and calls `feed_view.start_model_feed(m)` (`load_first` + hydrate). The model owns the bounded keyset window + cursor + live buffer; the view owns the geometry (scroll zones, anchor capture/restore, auto-continuation while pinned at a boundary, "N new posts" pill, end-of-DB sentinel). `make_post_widget(ev)` builds a PostWidget and registers `event_widgets[id]=w` on creation — that map is the dedup guard. `on_event_received` dedups against `event_widgets` (by event_id) and, for the following feed, calls `feed_model.prepend_new(ev)` (live buffer → pill → flush, or re-pull to promote) so switch_feed's DB cache + the live re-delivery of the same persisted events never render duplicates
- **Following-feed pagination (keyset):** `database.get_feed_following(owner, limit, before=None)` paginates on `(created_at DESC, id DESC)` — never OFFSET (degrades with depth, re-serves rows when events arrive mid-scroll). `before=(created_at, id)` is the previous page's tail; a page shorter than `limit` signals end-of-DB. Both pages hit `idx_events_feed (pubkey, kind, created_at)` — verified by EXPLAIN QUERY PLAN in `tests/test_feed_pagination.py`, which also guards the SQL against a regression to OFFSET (source scan, docstring-stripped)
- All async image loading goes through ImageLoader thread pool (max 16 workers, cache in dict)
- VideoPlayer uses `playbin3` GStreamer pipeline with `gtk4paintablesink` as video-sink — GStreamer renders frames to a `Gdk.Paintable` natively in C (no appsink / per-frame Python conversion), bound to a `Gtk.Picture`. Controls: `set_state(PLAYING/PAUSED)`, plays at full volume, **the video frame is the play/pause control** (no separate play button — lazy-start on first tap, toggle on later taps), mute button beside the seek bar; GIFs autoplay+loop without seek/mute controls. Real videos are **lazy-loaded** — no playbin3 pipeline is built (and no stream pulled) at render time; they show a placeholder graphic (a `Gtk.Overlay` with the play icon dead-centered and a "Play video" label anchored at the bottom) and build on first play tap via `ContentRenderer._start_playback` (removes placeholder, shows spinner, calls `load_and_play(autoplay=True)`), killing the measured 6+ concurrent-preroll contention; GIFs keep preroll+loop. The stutterers don't drop frames (QOS=0) — but **the sink runs with DEFAULT sync/async (True)**: a speculative `sync=False, async=False` made video play at high speed (removing the clock lets the sink render frames as fast as the decoder produces them instead of pacing to real time) and was reverted — do not disable clock sync to chase the freeze. GIFs keep preroll+loop ** and must pass `autoplay=True`** to `load_and_play` (omitting it — a lazy-load regression -- built the pipeline to PAUSED and left the spinner spinning with no playback). Player cache is a bounded LRU (`_CACHE_MAX=6`); evicted players set `_pipeline=None` and `_fetch_player` cache-hit treats a None pipeline as a miss so a dead/blank video is rebuilt fresh (fixes blank video after navigating away and back). Delivered frame size is capped at 720x406 (perf pass 2: Librem 5 feed widget is 360 logical px = 720 physical at scale 2, so 1280x720 converted/uploaded ~3x more pixels than reach the screen; override for A/B via GNOSTR_VIDEO_CAP=WxH, 0x0 disables). Frames are also rate-capped to 30fps via videorate drop-only BEFORE videoconvert (perf pass 2: the CPU NV12->RGBA convert is the measured bottleneck at ~1.4 A53 cores for 720p24, ~3 cores for 60fps sources; videorate halves it). Override via GNOSTR_VIDEO_FPS, 0 disables. The size cap is applied via a capsfilter bin wrapping the sink, with a `videoconvert` inside the bin for deterministic format adaptation (the capsfilter caps carry no `format`, which would otherwise make autoplug skip format conversion and fail on non-RGBA sources), and fallback to a direct sink. Perf pass 3 reorders that bin by MEASUREMENT: videorate -> `videoconvert` (n-threads, slice-parallel, ~2x on the Librem 5's 4x A53, override GNOSTR_VIDEO_THREADS clamped 1..8) -> `videoscale` -> capsfilter (format=RGBA + w/h range). Scale AFTER convert, never before: a w/h-range capsfilter upstream of the converter makes decodebin3 autoplug an NV12 videoscale that measured 38 s per 10 s clip (pathological) vs 10.4 s convert-then-scale. videoconvert cannot scale, so the explicit videoscale+caps live after it, inside the bin where autoplug cannot reach. GL offload explored and BLOCKED (pass 4): gstgl works in the sandbox (glimagesink renders; GPU NV12->RGBA + forced gldownload measured 4.3 s per 10 s 1080p60 clip vs 10.2 s CPU) but the embedded sink cannot use it: `gtk4glpaintablesink` is absent from the runtime and GDK cannot create a GL context there ('No EGL configuration available' — GSK runs cairo), so gtk4paintablesink is CPU-only. Do not retry glupload->gtk4paintablesink unless the runtime ships gtk4glpaintablesink AND ngl initializes. Trap: gldownload passes GLMemory through to any downstream with a plain video/x-raw template (subset caps match) and videoconvert passthroughs it; only a mapping element chokes (videoscale: 'code not implemented' per buffer, frames silently dropped — always check the warning count, not just wall time). Stutter diagnostics: the real dropped-frame signal is `GST_MESSAGE_QOS` (`1<<24`), matched with a numeric bitmask (enum names like `QOS`/`LATENCY`/`CLOCK_UPDATE` are inconsistently present across Flatpak bindings); QOS aggregates per-pipeline (`_qos_events`, `_qos_dropped`, `_qos_prop_min`) and a `PERF-QOS` summary (events + dropped_late + worst proportion + measured caps) prints at player eviction; state-changed lines carry the URL. `_inspect_pipeline` (decoder + caps report) runs via a 600ms `GLib.timeout_add` after first PAUSED/PLAYING so caps have time to negotiate (lazy-load autoplay races ahead of negotiation, so inline querying returned caps=None). `LATENCY` (`1<<19`) and other benign noise are not logged — they flooded the log and masked the QOS signal.
